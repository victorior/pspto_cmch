- (direction) Modo express: input de feature + brownfield budjetoc; slug carga-masiva-actividades-presupuesto.
- (decision) Why: pain — poblar actividades Presupuesto por tenant sin carga manual de encargados División/Coordinación; actor = super admin.
- (capability) CAP-1: Super admin accede a acción de carga masiva acotada a un tenant y crea actividades de presupuesto desde plantilla.
- (capability) CAP-2: Super admin descarga plantilla Excel-compatible con columnas y reglas documentadas.
- (capability) CAP-3: Super admin sube archivo por tenant; sistema valida filas contra catálogos/reglas y crea budget_headers + budget_details válidos.
- (capability) CAP-4: Tras el intento, informe de resultado (creadas/omitidas/errores por fila o grupo) visible al super admin.
- (constraint) Solo super admin (Auth::isSuperadmin / AdminAccess superadmin); no encargados ni tenant_admin.
- (constraint) Todo insert scoped por tenant_id del tenant elegido; no cruzar catálogos entre tenants.
- (constraint) Creación debe respetar BudgetActivityRules (división vs coordinación, CC obligatorio/null, receive-only no como creador).
- (constraint) UI admin + servicio reutilizable; no DocumentRoot fuera de public/; secretos fuera del zip/web.
- (constraint) Entrega: tests locales; commit+push a Main en GitHub; zip producción raíz budget/ vía _bmad-output/deploy/ para nanosoft.cl/budget.
- (decision) Objeto de carga = instancias presupuesto (budget_headers/details), no solo catálogo activities.
- (assumption) Plantilla alinea semántica con campos de creación actual + precedente Records2026 (agrupar cabecera + líneas detalle).
- (assumption) Por defecto create-only: si activity_number ya existe en el tenant, se omite (no overwrite), como Records2026.
- (assumption) Excel-compatible: .xlsx nativo o CSV/TSV editable en Excel; sin composer hoy — formato concreto es open question.
- (question) ¿Formato de archivo: .xlsx (nueva lib) o CSV/TSV Excel-compatible (patrón AdminUserCsvImportService)?
- (question) ¿created_by: departamento indicado en fila, o mapeo fijo cuando importa super admin?
- (question) ¿Vista previa dry-run obligatoria antes de confirmar la carga?
- (question) ¿Actualización de actividades existentes en scope, o solo altas?
- (note) Non-goals: carga por encargados; import OC/usuarios/catálogos genéricos; reemplazo del CLI Records2026; UI portal presupuesto para este botón.
- (note) Companions: brownfield.md, plantilla-import.md, delivery.md; adopted architecture-spine-budjetoc.md.

- (event) Self-validate Pass 1 (Coherence): CAP-1..4 have intent+success; intents WHAT; constraints bend design; non-goals present; success signal demonstrable; IDs stable; prose lean. PASS.
- (event) Self-validate Pass 2 (Preservation): super-admin button, per-tenant Excel template upload, populate Presupuesto activities, avoid encargado manual load, worktree/docs, local tests, Main push, nanosoft zip — all in SPEC or companions. Wrapper-only: none. PASS.

- (decision) created_by = departments.id del creador orgánico indicado en la fila de plantilla (División/Coordinación), no el user_id del super admin. No se exige auditoría de 'quién subió el archivo' como requisito de producto.

- (direction by user) Aclaración: es crítico saber a qué División o Coordinación se crean las actividades; no confundir con el user que sube.
- (decision) Cada actividad/grupo de la plantilla DEBE declarar creator_type + creator_name (División o Coordinación); eso persiste en created_by y reglas asociadas. Sin eso no hay carga válida.
- (event) Re-derivar SPEC/plantilla para dejar atribución orgánica inequívoca.

- (decision) Formato: CSV Excel-compatible, UTF-8 con BOM (o equivalente) para preservar tildes y eñes.
- (decision) Operador de la carga: siempre super admin. Atribución orgánica División/Coordinación sigue en columnas de plantilla → created_by (departments.id); el user SA no reemplaza esa FK.
- (decision) Validación previa obligatoria: informar cuántos registros se subirían y listar solo los que tienen error (para corregir archivo). Sin tabla de todos los records OK. Tras corregir, subir.
- (decision) Solo crear nuevos; si activity_number/id ya existe en DB, informar para que SA corrija el archivo (no upsert).
- (decision) UI debe ofrecer link/botón permanente para descargar la plantilla a completar.
